## Bugs

### BUG-1: Login returns 422 (with a field-level validation body) for an empty `identifier` or `password` instead of the generic 401
- **Severity:** Medium
- **Spec reference:** §6 rule 8 ("Login never returns 422 for a malformed identifier"), §7 login error table (422 only when `identifier`/`password` are *missing or not a string*), AC-15. The implementation's own `LoginRequest` description in `/openapi.json` states the same intent: *"a malformed identifier or a too-short password must come back as a generic 401, not a 422 that reveals the shape of real accounts"* — but the schema declares `minLength: 1` on both fields.
- **Steps to reproduce:**
  ```bash
  curl -s -i -X POST http://localhost:8000/api/v1/auth/login \
    -H 'content-type: application/json' -d '{"identifier":"","password":"qa-secret-123"}'

  curl -s -i -X POST http://localhost:8000/api/v1/auth/login \
    -H 'content-type: application/json' -d '{"identifier":"9999999999","password":""}'
  ```
- **Expected (per spec):** `401` with exactly `{"detail": "invalid phone/email or password"}` in both cases (an empty string is "an identifier that is neither a valid phone nor an email", and a too-short password is a credential mismatch).
- **Actual:** `422` with
  `{"detail":[{"type":"string_too_short","loc":["body","identifier"],"msg":"String should have at least 1 character","input":"","ctx":{"min_length":1}}]}`
  (and the equivalent for `password`).
- **Impact:** the login response shape now depends on the *form* of the input, which is the discrimination rule 8 is written to prevent, and the mobile screen (which renders `detail` verbatim, §9) would show an array instead of a message if the user submits an empty field and client-side zod validation is ever bypassed. Fix is one line: drop `min_length=1` from `LoginRequest`.

### BUG-2: The signup 422 body echoes the submitted password in plaintext
- **Severity:** Medium
- **Spec reference:** §6 rule 6 — "the plaintext is never stored, logged or returned"; AC-21 ("No response body contains … the password").
- **Steps to reproduce:**
  ```bash
  curl -s -X POST http://localhost:8000/api/v1/auth/signup \
    -H 'content-type: application/json' \
    -d '{"name":"QA","phone":"9876500011","password":"tiny"}'
  ```
- **Expected (per spec):** a 422 that does not contain the password value.
- **Actual:** `{"detail":[{"type":"string_too_short","loc":["body","password"],"msg":"String should have at least 8 characters","input":"tiny","ctx":{"min_length":8}}]}` — the plaintext lands in the response, and the same value also reaches any access/error log that records bodies.
- **Impact:** a near-miss password (the owner's real password minus a character, or the right password typed into the wrong field) is returned to the client and logged. Mitigation is small: validate the password length in a field validator that raises without echoing, or strip `input`/`ctx` from the 422 body for the `password` field with a custom `RequestValidationError` handler. Note §7 does say the 422 is "the FastAPI validation body", so this is also a spec contradiction (see Spec issue SI-1).

## Contract drift (spec vs /openapi.json)

Published paths are exactly `POST /api/v1/auth/signup`, `POST /api/v1/auth/login`,
`GET /api/v1/auth/me` plus F0.1's `GET /api/v1/health` — no out-of-scope routes, no `/pg`
(correctly deferred to F2). Documented status codes match §7 (signup 201/409/422, login
200/401/422, me 200/401); `AuthResponse`, `OwnerRead`, `SignupRequest` field sets match §7
exactly; `token_type` is `const: "bearer"`; `OwnerRead` has no `password_hash`; `/auth/me`
is the only operation with `security: [{HTTPBearer: []}]`.

Two low-severity mismatches:

1. **Low — `LoginRequest` declares `minLength: 1` on `identifier` and `password`.** §7 lists no
   length validation for login, and rule 8 forbids a 422 for a malformed identifier. This is
   the schema-level cause of BUG-1.
2. **Low — `OwnerRead.email` is typed `string | null` with no `format: email`.** §7's
   `OwnerRead` mirrors the stored value, so this is cosmetic; worth noting only because
   `SignupRequest.email` does carry `format: email`. No behavioural impact.

## Spec issues and open questions

- **SI-1 (contradiction).** §6 rule 6 says the plaintext password is "never … returned", while
  §7 says a password-length failure returns "FastAPI validation body" — whose default `input`
  field contains that very plaintext. The spec should say explicitly whether the 422 body must
  be sanitised for the `password` field. Reported as BUG-2 against rule 6, since rule 6 is the
  stronger, security-relevant statement.
- **SI-2 (gap).** §6 rule 8 and §7 do not say what should happen when `identifier` or `password`
  is an **empty string**. Rule 8's wording ("an identifier that is not a valid phone or email …
  return 401") points to 401, and that is how the tests are written, but the spec would be
  clearer with the empty-string case named. Pydantic's `min_length=1` currently wins.
- **SI-3 (minor).** §7's `AuthResponse`/`OwnerRead` examples show `created_at` with the IST
  offset (`+05:30`), while §6 rule 13 only requires "timezone-aware". The app does return
  `+05:30`, and the test asserts the example's offset — worth stating as a rule rather than
  leaving it to the example, since F3+ clients will parse this.
- **SI-4 (observation, not a defect).** The spec's `normalize_phone` table does not say whether
  separators are allowed inside bare 10/11/12-digit inputs (e.g. `98765 43210`, `(98765) 43210`,
  `98765.43210`). The implementation strips them and accepts all of these, which matches
  CLAUDE.md §7's examples; the tests assume that behaviour.

## Not black-box testable

1. **AC-2 / AC-21 (stored hash) / AC-23 / AC-29** — the `pgs` row, `password_hash` and the table
   constraints have no HTTP surface in F1 (`GET /pg` lands in F2). They were verified with
   read-only `SELECT`s against `pgrent_dev` plus one deliberately failing `INSERT` inside a
   rolled-back transaction (`qa/tests/test_F1_auth_db.py`). This is grey-box, not black-box;
   it uses the data, never the code. Once F2 ships `GET /pg`, AC-2 should move to a pure HTTP test.
2. **AC-19 expiry via the real clock** — the server clock cannot be frozen from outside, so the
   expired token was forged with the `JWT_SECRET` from `backend/.env`. The code path (PyJWT
   `exp` validation) is the same, but this cannot catch a mistake in how the app *computes* `exp`;
   that is covered indirectly by `test_AC1_signup_token_claims` (`exp - iat == 43200 min`).
3. **Argon2 parameters / cost (§11)** — not observable over HTTP beyond latency (~130 ms per login
   on this machine, consistent with default `PasswordHasher` settings).
4. **Token non-revocability after logout (§11)** — by design there is nothing server-side to observe.
5. **All mobile criteria (AC-24 … AC-28, AC-30)** — require the device/emulator and the Jest suite.

### Observations (not pass/fail)
- **Login timing leak closed.** Medians over 6 requests each: wrong password 137 ms, unknown phone
  133 ms, malformed identifier 126 ms. The `DUMMY_HASH` verification in §8 step 11 works; account
  existence is not distinguishable by timing at this resolution.
- **No rate limiting**, as §3 states. 6 concurrent signups and dozens of failed logins were
  accepted without throttling. Out of scope for the MVP; flagged for the deploy step.
- **`JWT_SECRET` in `backend/.env` is still the placeholder** from `.env.example`
  (`change-me-in-production-…`). Fine locally (and it is what made AC-19/AC-20 testable), but it
  must be a real secret before any deploy — §11 already flags this.
- The API was not running when this session started. QA started `uvicorn` on 127.0.0.1:8000 against
  `pgrent_dev` for the duration of the run and **stopped it again afterwards**, so the environment is
  back in the state it was found in. Test owners created by this run remain in `pgrent_dev`; they all
  have unique random phone numbers and do not collide with the developer's own account.

## How to re-run

```bash
# the API must be running: cd backend && uv run uvicorn app.main:app
pip install -r qa/requirements.txt
QA_BASE_URL=http://localhost:8000 pytest qa/tests/test_F1_auth.py qa/tests/test_F1_auth_db.py -v
```

`qa/tests/test_F1_auth_db.py` reads `DATABASE_URL` from `backend/.env` and skips itself if that
file is absent. Both files create every owner they need with a fresh random phone number, so they
are safe to re-run against a database that already holds data.
