## Spec issues and open questions

### SI-1 — AC-8 and §8 step 3 disagree about type coercion on `default_rent_due_day`
AC-8 and §7's table say the value "must be an integer (`5.5`, `"abc"`, `null` → 422)". §8 step 3
prescribes `Annotated[int, Field(ge=1, le=28)]` plus a bool guard — and Pydantic's lax mode then
accepts JSON values that are not integers:

```bash
curl -s -X PATCH localhost:8000/api/v1/pg -H "Authorization: Bearer $T" \
  -H 'Content-Type: application/json' -d '{"default_rent_due_day":"7"}'
# 200 → "default_rent_due_day":7      (also ' 8 ' → 8, and 9.0 → 9)
```

Impact is low: whatever gets through is still a whole number inside 1–28, and the mobile card sends
`Number(dueDay)`. But the spec can't be both "must be an integer" and "a plain `int` field". Decide
one and write it down: either keep lax coercion and reword AC-8 to "not coercible to an integer in
1–28", or add `strict=True` to the field and make `"7"` a 422. Pinned by
`test_update_pg_rejects_coercible_due_day` (currently `xfail`, flipping to a failure the moment the
behaviour tightens, which is the signal you want).

### SI-2 — "trimmed" is specified for `address` in §7 but not in §6 rule 6 or §8 step 3
§7's `PgUpdate` table says `address` is "trimmed; `""`/whitespace → `None`", while rule 6 only
mentions the blank→`NULL` conversion and §8 step 3 only puts `_trim` on `name`. The app does trim
(`"  12, 4th Cross  "` → `"12, 4th Cross"`), which matches §7, so no action is needed — but rule 6
should say so explicitly, since it is the section a future reader will treat as normative.

### Open questions
1. **Unknown body keys are silently ignored.** `{"unknown_field": "x"}` returns 200 and changes
   nothing; so does `{"owner_id": …}`. Harmless today, but the spec never states whether `PgUpdate`
   should forbid extras. A typo like `{"nmae": "Sri Sai PG"}` currently looks like a successful save.
   Worth settling before F3/F4 add bigger bodies.
2. **A completely absent body is a 422, not the `{}` no-op of §12 Q7.** `PATCH /pg` with no body at
   all returns `{"detail":[{"type":"missing","loc":["body"]…}]}`. Defensible, and no client does it,
   but Q7's wording ("a request that asks for no change") arguably covers it.
3. **Address trim vs the 500-char cap order.** Not specified: is a 505-character address with 6
   leading spaces (499 after trimming) accepted? Untested here because the spec gives no expected
   answer.
4. **Pre-existing F1 bugs are still open** and still reproduce on this build (not F2 regressions,
   listed for completeness): `POST /auth/login` with an empty `identifier`/`password` returns 422
   instead of the generic 401 (F1 BUG-1), and the signup 422 body still echoes the submitted
   password in `input` (F1 BUG-2). `qa/tests/test_F1_auth.py` reports exactly these 3 failures.

## Not black-box testable

Nothing in F2's backend scope. For the record, the three criteria that are not reachable through the
public API were covered with read-only/throwaway SQL against `pgrent_dev` instead, which is still
black-box with respect to the application code:

- **AC-15** — `updated_at` is deliberately not in `PgRead`, so the bump was verified by reading the row.
- **AC-14** — "owner has no PG row" cannot be produced through the API (no `DELETE /pg` by design), so
  the row was deleted with SQL for a throwaway owner.
- **AC-22** — the DB check constraint is by definition below the API.

AC-16, AC-17, AC-18, AC-20 and AC-23 are mobile-UI criteria: not testable from outside the API at all
(not merely hard), so they are listed as manual rather than as results.

## How to re-run

```bash
# backend (if not already running)
cd backend && uv run alembic upgrade head && uv run uvicorn app.main:app --port 8000

# QA suite — needs pytest, httpx, pyjwt and psycopg from qa/requirements.txt
QA_BASE_URL=http://localhost:8000 pytest qa/tests/test_F2_pg.py -v
```

`pyjwt` is used to forge expired / foreign-signed tokens and `psycopg` for AC-14/15/22; both are
skipped (`importorskip`) if absent, and `psycopg` reads `DATABASE_URL` from `backend/.env`. The tests
create their own owners with random phone numbers, so they are safe to re-run and never depend on
leftover data — but they do write to `pgrent_dev`, never to a production database.
