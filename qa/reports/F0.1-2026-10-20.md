## Contract drift (spec vs /openapi.json)
- **Low:** Spec §7 defines an error response `503 {"detail": "database unavailable"}`, and
  the operation description in OpenAPI mentions it, but the `responses` object of
  `/api/v1/health` only documents `200`. The 503 is raised via `HTTPException` so FastAPI
  does not auto-document it. Cosmetic only; behaviour was not contradicted. Consider adding
  an explicit `responses={503: ...}` to the route decorator so the published contract matches §7.

No other drift: the single published path is `GET /api/v1/health`, matching the spec, and no
domain endpoints are exposed (consistent with §3 "zero tables / no domain models").

## Not black-box testable
1. **DB-down → 503** (§7, `test_health_db_down`). Verifying this requires making Postgres
   unreachable. The only ways are stopping the system Postgres service or overriding the
   `get_db` dependency — both require touching the shared dev DB / server or the app's test
   harness, which is out of bounds for external black-box QA and would disrupt the running
   instance. Covered by the spec's own unit test (dependency override) and manual step 8.
2. **`alembic upgrade head` on an empty DB + idempotency** (§11, `test_migrations_upgrade_head`).
   Not exposed over HTTP; it is a build/harness concern requiring DB access. Covered by manual
   steps 5–6.
3. **`pytest` suite passes** (§11). This is the application's internal test suite, not an
   external runtime surface. Covered by manual step 9.
